# 面接で話せる論点メモ（INTERVIEW_NOTES）

このアプリの**事実と設計判断**だけをまとめています。
開発のきっかけや感想などの「自分の言葉」は、ここには書いていません。自分の経験に合わせて肉付けしてください。

---

## 1. どんなアプリか（30 秒で）
- 留学生が体験したカルチャーショックを、匿名で投稿・共有する Web アプリ。
- リアクションは「共感（それわかる！）」と「発見（そんなのあるんだ！）」の 2 種類。
- コメントや DM は作らず、「読む」と「リアクション」に機能を絞った。
- Next.js（App Router）＋ Supabase で作り、Vercel で公開。

## 2. 技術選定の理由

| 選んだもの | 理由 | 比べたもの・トレードオフ |
|---|---|---|
| Next.js（App Router） | 画面とサーバー処理を 1 つのプロジェクトで書ける。Server Component で一覧を取得すると、表示が速く、DB 接続の情報をブラウザに出さずに済む | 学習コストは高め（Server / Client の区別） |
| Supabase | PostgreSQL・ログイン・API がそろっていて、サーバーを自前で用意せずに済む。RLS で DB 自身にアクセス制御を持たせられる | 公開キーがブラウザに配られる前提なので、DB 側の守り（RLS・権限）を正しく書く必要がある |
| JavaScript（TypeScript なし） | 学習目的で、まず全体の流れを理解することを優先 | 型による誤りの検出はない。入力チェック関数とテストで補った |
| Tailwind CSS | 色や角丸をテーマとして一元管理でき、部品ごとの見た目を 1 ファイルで完結できる | クラス名が長くなりやすい |
| 国旗を SVG で表示 | 国旗の絵文字は Windows で「US」のような文字になってしまう | 使う国だけを import して、データ量を抑えた |

## 3. 匿名性と信頼性の両立

- **名前は一切表示しない**。ログインなしでも投稿できるようにして、投稿の心理的ハードルを下げた。
- 一方で、匿名だけだと内容の信頼感が出にくい。そこで、ログインユーザーは任意で
  **「アメリカ留学10ヶ月」のような留学バッジ**を付けられるようにした。
- バッジは**投稿した時点の値を `posts` テーブルに保存**（スナップショット）。
  こうすると、他人に `profiles`（プロフィール）を読ませる必要がなく、誰の投稿かをたどれない。
- バッジの値は DB のトリガーが**本人のプロフィールで上書き**するので、API を直接叩いて偽ることもできない。
- `posts.user_id` は DB 上では持っているが、**列の権限で誰にも読ませない**。
  「自分の投稿か」の判定（削除メニューの表示）は、ログイン中の本人の分だけ返す DB 関数で行う。

## 4. セキュリティ設計

| 脅威 | 対策 | どこで |
|---|---|---|
| 公開キーで API を直接叩かれる | 4 テーブルすべてで RLS を有効化し、必要最小限のポリシーだけ作成。さらに列単位の権限で、書ける列・読める列を絞った | `supabase/schema.sql` |
| いいね数のような件数の改ざん | `posts` の UPDATE 権限を誰にも渡さず、件数はトリガーだけが増減する | `sync_reaction_counts` |
| 1 人で何度もリアクション・通報 | UNIQUE 制約 (post_id, user_id) | `reactions` / `reports` |
| 他人になりすました投稿 | RLS で `user_id` は NULL か自分の ID のみ | posts の INSERT ポリシー |
| 他人の投稿の削除 | RLS で `user_id = auth.uid()` の行だけ削除可能 | posts の DELETE ポリシー |
| ブラウザ側の入力チェックのすり抜け | サーバー（Server Action）でも同じ関数でチェック。さらに DB の CHECK 制約 | `lib/validation.js` |
| XSS（スクリプトの埋め込み） | `dangerouslySetInnerHTML` を使わず、React の自動エスケープに任せる。リンクの自動リンク化もしない | `PostCard.js` |
| ログイン後の外部サイトへの誘導 | 戻り先 `next` をサイト内のパスに限定 | `safeNextPath()` |
| 秘密情報の漏えい | `.env.local` は git 管理外。RLS を無視できる secret key はアプリで一切使わない | ― |

**多層防御の考え方**: ブラウザ → Server Action → DB（権限・RLS・トリガー・制約）の順に何重にもチェックし、
どこか 1 か所にバグがあっても DB がおかしな値を受け付けないようにした。

## 5. 実装で工夫した点

- **楽観的更新**: リアクションは押した瞬間に数字が変わり、失敗したら元に戻してエラーを出す（`useOptimistic`）。
  サーバーには「押した種類」ではなく「押した後の状態」を送るので、連打しても最終的な状態がずれない。
- **URL で状態を持つ**: 国の絞り込みと並び替えは `/?country=US&sort=empathy` のように URL に入れた。
  リロード・共有・ブラウザの戻るで同じ画面が再現できる。
- **「もっと見る」と再取得の両立**: 投稿後にサーバーから届く最新の 1 ページ目と、追加で読み込んだ分を合体させ、
  読み込んだ分が消えないようにした。
- **アクセシビリティ**: HTML 標準の `<dialog>` でフォーカスの閉じ込めと Esc を実現。
  文字色はすべて WCAG AA（4.5:1）以上を計算で確認。リアクションの状態は色だけでなくアイコンでも示す。
  タップ領域は 44px 以上。`prefers-reduced-motion` で動きを止める。
- **検証**: DB の設計（RLS・トリガー）は、手元の疑似 Postgres（PGlite）でテストしてから本番に適用した。
  画面の動作はブラウザ自動操作（Playwright）で、フェーズごとに確認した。

## 6. トレードオフ（あえてやらなかったこと）

| やらなかったこと | 理由 | 必要になったら |
|---|---|---|
| スパム対策（ボット対策・投稿頻度の制限） | MVP では機能を絞ることを優先。匿名投稿はできるが、リアクションと通報はログイン必須にして悪用の影響を抑えた | Cloudflare Turnstile などの導入を検討 |
| 通報の管理画面 | 非表示投稿の復活・削除は、運営者が Supabase のダッシュボードで手動対応する | 管理者ロールと画面を追加 |
| 確認メール | 登録の手間を減らすため MVP ではオフ | 本番運用でオンにする |
| 投稿の編集 | 機能を絞るため。削除して再投稿してもらう | ― |
| コメント・DM | 「読む・反応する」に特化し、やり取りによるトラブルを避けるため | ― |
| 3 件で自動非表示 | 少ない件数で非表示にすると、正当な投稿が悪意ある通報で消えるリスクがある。一方で放置もしたくない。ログイン必須・1 人 1 回にしたうえで、件数は MVP として 3 件にした | 件数の調整や、運営の確認を挟む仕組み |
| オフセット方式のページング | 実装が簡単。読み込み中に新しい投稿が増えると重複しうるので、ID で重複を除いている | 件数が増えたらカーソル方式（最後の投稿の日時で続きを取る）に |

## 7. 想定される質問と、答えの材料

- **Q. RLS とは？ なぜ必要？**
  → DB が行ごとにアクセスを判定する仕組み。Supabase は公開キーがブラウザに配られるので、
  アプリのコードだけで守ると API を直接叩かれたときに破られる。DB 側で守る必要がある。
- **Q. Server Component と Client Component はどう使い分けた？**
  → データ取得は Server Component（`PostFeed.js`）、クリックや入力のある部品は Client Component
  （`ReactionButtons.js` など）。DB の書き換えはすべて Server Action（`lib/actions/`）に集めた。
- **Q. 件数の整合性はどう保証している？**
  → 件数は `reactions` テーブルの変化をきっかけに、トリガーだけが増減させる。UNIQUE で 1 人 1 つ、
  `posts` の UPDATE 権限は誰にもない。
- **Q. 匿名なのに自分の投稿を削除できるのはなぜ？**
  → DB では `user_id` で紐づけているが、その列は誰にも読ませていない。「自分の投稿か」は、
  ログイン中の本人の分だけを返す DB 関数で判定している。
